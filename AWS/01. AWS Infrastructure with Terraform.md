## 1. Introduction to Terraform and IaC

### What Is Infrastructure as Code?

**Infrastructure as Code (IaC)** means managing and provisioning infrastructure through machine-readable configuration files instead of manual processes or interactive UIs. Instead of clicking through the AWS Console to create servers, networks, and databases, you describe your desired state in code.

**Benefits of IaC:**

| Benefit | Description |
|---|---|
| **Repeatability** | Spin up identical environments every time |
| **Version control** | Track every infrastructure change in Git |
| **Speed** | Provision entire environments in minutes |
| **Auditability** | Know exactly what changed, when, and by whom |
| **Cost control** | Tear down environments you're not using |

### What Is Terraform?

**Terraform** is an open source IaC tool created by HashiCorp. It uses a declarative configuration language called **HCL (HashiCorp Configuration Language)** to define infrastructure resources across hundreds of providers: AWS, Azure, GCP, Kubernetes, and more.

Key concepts:

- **Provider**: a plugin that translates your HCL into API calls (e.g., the AWS provider)
- **Resource**: a single infrastructure object (e.g., an EC2 instance, an S3 bucket)
- **Data source**: reads existing infrastructure without managing it
- **Module**: a reusable package of Terraform configurations
- **State**: a file that maps your configuration to real world resources
- **Workspace**: an isolated instance of state for the same configuration

## 2. Prerequisites and Setup

### 2.1 AWS Account and IAM Setup

#### Create an AWS Account
If you don't already have one, sign up at [https://aws.amazon.com](https://aws.amazon.com). A free tier account is sufficient for this tutorial.

#### Create an IAM User for Terraform

> Never use root account credentials with Terraform. Always create a dedicated IAM user.

1. Sign in to the [AWS Console](https://console.aws.amazon.com).
2. Navigate to **IAM > Users > Create user**.
3. Name the user `terraform-lab` (or similar).
4. Select **Attach policies directly**.
5. For this tutorial, attach `AdministratorAccess` (for learning only).

> In real environments, scope permissions to the minimum required resources using least privilege policies.

6. Click **Create user**.
7. Open the user > **Security credentials** > **Create access key**.
8. Choose **Command Line Interface (CLI)**.
9. Download the `.csv` file or copy the **Access key ID** and **Secret access key**. You will not be able to view the secret again.

## 3. Your First Terraform Project

### 3.1 Project Structure

Create a working directory for the project:

```bash
# Linux/macOS
mkdir ~/terraform-aws-lab && cd ~/terraform-aws-lab

# Windows PowerShell
mkdir C:\Users\$env:USERNAME\terraform-aws-lab
cd C:\Users\$env:USERNAME\terraform-aws-lab
```

You will create the following files:

```
terraform-aws-lab/
├── terraform.tf      # Required providers and Terraform settings
├── main.tf           # Resource definitions
├── variables.tf      # Input variable declarations
└── outputs.tf        # Output value declarations
```

> **Convention:** Terraform loads all `.tf` files in a directory. File names are a convention, not a requirement — but following this structure makes projects easier to navigate.

### 3.2 Configuring the AWS Provider

Create `terraform.tf`:

```hcl
# terraform.tf

terraform {
  required_version = ">= 1.3.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}
```

**Explanation:**

| Block | Purpose |
|---|---|
| `terraform {}` | Global Terraform settings |
| `required_version` | Enforces minimum Terraform CLI version |
| `required_providers` | Declares provider plugins and their versions |
| `provider "aws" {}` | Configures the AWS provider |
| `~> 5.0` | Version constraint: `>= 5.0, < 6.0` |

The `var.aws_region` reference means we'll define an `aws_region` variable shortly.

### 3.3 Using Data Sources

Data sources let you fetch information about existing AWS resources without creating or managing them. Here we retrieve the most recent Amazon Linux 2023 AMI automatically.

Add this to `main.tf`:

```hcl
# main.tf

# Retrieve the latest Amazon Linux 2023 AMI
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }
}
```

**Why use a data source for AMIs?**  
AMI IDs are region-specific and change when Amazon releases new versions. Using a data source ensures you always get the latest AMI without hardcoding a value that will become outdated.

Reference the data source as: `data.aws_ami.amazon_linux.id`

### 3.4 Creating an EC2 Instance

Append the following to `main.tf`:

```hcl
# main.tf (continued)

# Security group for the EC2 instance
resource "aws_security_group" "web_sg" {
  name        = "${var.project_name}-web-sg"
  description = "Allow HTTP and SSH traffic"

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"] # Restrict to your IP in production
  }

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "${var.project_name}-web-sg"
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}

# EC2 instance
resource "aws_instance" "web" {
  ami                    = data.aws_ami.amazon_linux.id
  instance_type          = var.instance_type
  vpc_security_group_ids = [aws_security_group.web_sg.id]

  user_data = <<-EOF
    #!/bin/bash
    yum update -y
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    echo "<h1>Deployed by Terraform on $(hostname)</h1>" > /var/www/html/index.html
  EOF

  tags = {
    Name        = "${var.project_name}-web"
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}
```

**Key concepts:**

- `resource "aws_instance" "web"` — resource type is `aws_instance`, local name is `web`
- `data.aws_ami.amazon_linux.id` — references the AMI data source
- `aws_security_group.web_sg.id` — references another resource in the same config (implicit dependency)
- `user_data` — a shell script that runs at EC2 first boot (installs Apache)
- `<<-EOF ... EOF` — a heredoc for multi-line strings
- `${var.project_name}` — string interpolation using a variable

## 4. The Terraform Workflow

### 4.1 `terraform init`

Initialize the working directory. This downloads the required providers.

```bash
terraform init
```

Expected output:
```
Initializing the backend...
Initializing provider plugins...
- Finding hashicorp/aws versions matching "~> 5.0"...
- Installing hashicorp/aws v5.x.x...
- Installed hashicorp/aws v5.x.x (signed by HashiCorp)

Terraform has been successfully initialized!
```

This creates:
- `.terraform/` — provider plugins (do not commit to Git)
- `.terraform.lock.hcl` — provider version lock file (commit to Git)

Re-run `terraform init` whenever you add or change providers or modules.

### 4.2 `terraform validate`

Check your configuration for syntax errors without contacting AWS:

```bash
terraform validate
```

Expected output:
```
Success! The configuration is valid.
```

Common errors caught by validate:
- Missing required arguments
- Invalid attribute names
- Syntax errors in HCL

### 4.3 `terraform plan`

Preview what Terraform will create, modify, or destroy before touching real infrastructure:

```bash
terraform plan
```

Terraform will prompt for any variables not yet defined. If you have defined a `variables.tf` file (see section 5), it reads defaults from there.

Expected output (excerpt):
```
Terraform will perform the following actions:

  # aws_instance.web will be created
  + resource "aws_instance" "web" {
      + ami                    = "ami-0abcdef1234567890"
      + instance_type          = "t2.micro"
      + tags                   = {
          + "Environment" = "dev"
          + "ManagedBy"   = "Terraform"
          + "Name"        = "terraform-lab-web"
        }
      ...
    }

  # aws_security_group.web_sg will be created
  + resource "aws_security_group" "web_sg" {
      ...
    }

Plan: 2 to add, 0 to change, 0 to destroy.
```

**Legend:**
- `+` resource will be created
- `-` resource will be destroyed
- `~` resource will be updated in-place
- `-/+` resource will be destroyed and re-created

Save a plan to a file for use with apply:
```bash
terraform plan -out=tfplan
```

### 4.4 `terraform apply`

Apply the planned changes to your AWS account:

```bash
terraform apply
```

Terraform shows the plan again and asks for confirmation:
```
Do you want to perform these actions?
  Terraform will perform the actions described above.
  Only 'yes' will be accepted to approve.

  Enter a value: yes
```

Type `yes` and press Enter.

Expected output:
```
aws_security_group.web_sg: Creating...
aws_security_group.web_sg: Creation complete after 2s [id=sg-0abc123]
aws_instance.web: Creating...
aws_instance.web: Still creating... [10s elapsed]
aws_instance.web: Creation complete after 32s [id=i-0abc1234567890def]

Apply complete! Resources: 2 added, 0 changed, 0 destroyed.
```

To skip the confirmation prompt (useful in CI/CD):
```bash
terraform apply -auto-approve
```

To apply a saved plan file:
```bash
terraform apply tfplan
```

### 4.5 `terraform destroy`

Remove all resources managed by Terraform in the current directory:

```bash
terraform destroy
```

Expected output:
```
Plan: 0 to add, 0 to change, 2 to destroy.

Do you really want to destroy all resources?
  Enter a value: yes

aws_instance.web: Destroying...
aws_instance.web: Destruction complete after 30s
aws_security_group.web_sg: Destroying...
aws_security_group.web_sg: Destruction complete after 2s

Destroy complete! Resources: 2 destroyed.
```

> **Always run `terraform destroy` when done with lab environments** to avoid unexpected AWS charges.

To destroy only a specific resource:
```bash
terraform destroy -target=aws_instance.web
```

## 5. Input Variables

Variables make your Terraform code reusable and configurable.

Create `variables.tf`:

```hcl
# variables.tf

variable "aws_region" {
  description = "AWS region for all resources"
  type        = string
  default     = "us-east-1"
}

variable "project_name" {
  description = "A prefix used to name all created resources"
  type        = string
  default     = "terraform-lab"
}

variable "environment" {
  description = "Deployment environment (dev, staging, prod)"
  type        = string
  default     = "dev"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be one of: dev, staging, prod"
  }
}

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t2.micro"
}
```

**Variable types:**

| Type | Example |
|---|---|
| `string` | `"t2.micro"` |
| `number` | `3` |
| `bool` | `true` |
| `list(string)` | `["us-east-1", "us-west-2"]` |
| `map(string)` | `{ env = "dev" }` |
| `object({...})` | `{ name = string, count = number }` |

#### Ways to Set Variable Values

**1. Default values** (in `variables.tf`) — used automatically.

**2. `.tfvars` file** — create `terraform.tfvars` (auto-loaded):
```hcl
# terraform.tfvars
aws_region    = "us-west-2"
project_name  = "my-project"
environment   = "staging"
instance_type = "t3.small"
```

**3. Environment variables** — prefix `TF_VAR_`:
```bash
# Linux/macOS
export TF_VAR_environment=prod

# Windows PowerShell
$env:TF_VAR_environment = "prod"
```

**4. Command-line flags:**
```bash
terraform apply -var="environment=prod" -var="instance_type=t3.medium"
```

**Variable precedence** (lowest to highest):
1. Default values
2. `terraform.tfvars`
3. `*.auto.tfvars` files
4. `-var-file` flag
5. `-var` flag
6. `TF_VAR_*` environment variables

## 6. Output Values

Outputs expose useful information after `apply` — like IP addresses or resource IDs.

Create `outputs.tf`:

```hcl
# outputs.tf

output "instance_id" {
  description = "The ID of the EC2 instance"
  value       = aws_instance.web.id
}

output "instance_public_ip" {
  description = "The public IP address of the EC2 instance"
  value       = aws_instance.web.public_ip
}

output "instance_public_dns" {
  description = "The public DNS name of the EC2 instance"
  value       = aws_instance.web.public_dns
}

output "web_url" {
  description = "URL to access the web server"
  value       = "http://${aws_instance.web.public_ip}"
}

output "security_group_id" {
  description = "The ID of the web security group"
  value       = aws_security_group.web_sg.id
}
```

After `terraform apply`, outputs are shown automatically:

```
Outputs:

instance_id         = "i-0abc1234567890def"
instance_public_dns = "ec2-1-2-3-4.compute-1.amazonaws.com"
instance_public_ip  = "1.2.3.4"
security_group_id   = "sg-0abc123"
web_url             = "http://1.2.3.4"
```

View outputs at any time:
```bash
terraform output                    # All outputs
terraform output instance_public_ip # One output
terraform output -json              # JSON format (useful for scripts)
```

Mark sensitive outputs (hides value in terminal):
```hcl
output "db_password" {
  value     = aws_db_instance.main.password
  sensitive = true
}
```

## 7. Managing Infrastructure Changes

Terraform determines what changes to make by comparing your configuration against the current **state**.

### Modify the EC2 Instance Type

Edit `variables.tf` to change the default:
```hcl
variable "instance_type" {
  default = "t3.small"   # Changed from t2.micro
}
```

Run plan to preview the change:
```bash
terraform plan
```

Terraform output:
```
  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
        id            = "i-0abc1234567890def"
      ~ instance_type = "t2.micro" -> "t3.small"
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

`~` means update in-place — the instance will be stopped, resized, and restarted.

### Force Resource Recreation

Some changes require destroying and recreating a resource (e.g., changing the AMI). Terraform marks these as `-/+`:

```
  # aws_instance.web must be replaced
-/+ resource "aws_instance" "web" {
      ~ ami           = "ami-old" -> "ami-new" # forces replacement
    }

Plan: 1 to add, 0 to change, 1 to destroy.
```

> **Warning:** Resource recreation causes downtime. Always review plans carefully.

### Add Tags Without Downtime

Tags are updated in-place. Add to `main.tf`:
```hcl
tags = {
  Name        = "${var.project_name}-web"
  Environment = var.environment
  ManagedBy   = "Terraform"
  Owner       = "your-team"    # new tag
  CostCenter  = "engineering"  # new tag
}
```

```
  ~ resource "aws_instance" "web" {
      ~ tags = {
          + "CostCenter" = "engineering"
          + "Owner"      = "your-team"
        }
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

## 8. Terraform State

### What Is State?

Terraform stores a mapping between your configuration and real-world resources in a **state file** (`terraform.tfstate`). This file is the source of truth for Terraform.

The state file includes:
- Resource IDs and attributes
- Dependency graph
- Outputs

### Inspecting State

```bash
# List all resources in state
terraform state list

# Show details for a specific resource
terraform state show aws_instance.web

# Show all state as JSON
terraform show -json
```

Example output of `terraform state show aws_instance.web`:
```
# aws_instance.web:
resource "aws_instance" "web" {
    ami                    = "ami-0abcdef1234567890"
    id                     = "i-0abc1234567890def"
    instance_type          = "t2.micro"
    public_ip              = "1.2.3.4"
    tags                   = {
        "Environment" = "dev"
        "ManagedBy"   = "Terraform"
        "Name"        = "terraform-lab-web"
    }
    ...
}
```

### State Operations

```bash
# Remove a resource from state without destroying it
terraform state rm aws_instance.web

# Import an existing resource into state
terraform import aws_instance.web i-0abc1234567890def

# Move a resource in state (rename)
terraform state mv aws_instance.web aws_instance.app_server
```

### Why Local State Is Risky

Local `terraform.tfstate` files have problems in team environments:
- **No locking** — two people applying at once corrupts state
- **No sharing** — team members can't see each other's state
- **No backup** — accidental deletion loses all state

This is why we use remote state (covered in section 11).

## 9. Using Terraform Registry Modules

The [Terraform Registry](https://registry.terraform.io) hosts thousands of reusable modules. Using community modules saves time and implements proven best practices.

### 9.1 Deploying a VPC with the Official AWS VPC Module

The official `terraform-aws-modules/vpc/aws` module creates a full VPC with subnets, route tables, and gateways.

Add to `main.tf`:

```hcl
# main.tf — VPC Module

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"

  name = "${var.project_name}-vpc"
  cidr = var.vpc_cidr

  azs             = data.aws_availability_zones.available.names
  private_subnets = var.private_subnet_cidrs
  public_subnets  = var.public_subnet_cidrs

  enable_nat_gateway   = true
```

```hcl
    to_port     = 0

  instance_type               = var.instance_type

  vpc_security_group_ids      = [aws_security_group.web_sg.id]

  user_data = <<-EOF

    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
```

## 11. Terraform Best Practices

### 11.1 Remote State with S3 and DynamoDB

Remote state stores `terraform.tfstate` in S3 with locking via DynamoDB, enabling team collaboration.

#### Step 1: Create S3 Bucket and DynamoDB Table

First, create these resources manually or with a bootstrap Terraform config:

```bash
# Create S3 bucket (replace ACCOUNT_ID with your AWS account ID)
aws s3api create-bucket \
  --bucket terraform-state-ACCOUNT_ID \
  --region us-east-1

# Enable versioning (recover previous state if needed)
aws s3api put-bucket-versioning \
  --bucket terraform-state-ACCOUNT_ID \
  --versioning-configuration Status=Enabled

# Enable server-side encryption
aws s3api put-bucket-encryption \
  --bucket terraform-state-ACCOUNT_ID \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      }
    }]
  }'

# Block all public access
aws s3api put-public-access-block \
  --bucket terraform-state-ACCOUNT_ID \
  --public-access-block-configuration \
  "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

# Create DynamoDB table for state locking
aws dynamodb create-table \
  --table-name terraform-locks \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --region us-east-1
```

#### Step 2: Configure the S3 Backend

Update `terraform.tf`:

```hcl
# terraform.tf — with remote backend

terraform {
  required_version = ">= 1.3.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  backend "s3" {
    bucket         = "terraform-state-ACCOUNT_ID"  # Replace with your bucket
    key            = "terraform-aws-lab/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}

provider "aws" {
  region = var.aws_region
}
```

#### Step 3: Migrate State

```bash
terraform init -migrate-state
```

Terraform asks:
```
Do you want to copy existing state to the new backend?
Enter a value: yes
```

Your state is now stored in S3 and locked when in use.

### 11.3 Security and Credential Management

**Never hardcode credentials in .tf files.**

```hcl
# BAD — never do this
provider "aws" {
  access_key = "AKIAIOSFODNN7EXAMPLE"
  secret_key = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
}

# GOOD — use environment variables or IAM roles
provider "aws" {
  region = var.aws_region
  # Credentials from ~/.aws/credentials, env vars, or IAM role
}
```

**Use IAM Roles in CI/CD:** Configure your CI/CD pipeline (GitHub Actions, GitLab CI, Jenkins) to assume an IAM role using OIDC rather than storing static credentials.

**Use AWS Secrets Manager for app secrets:**
```hcl
data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "prod/app/db-password"
}

# Reference: data.aws_secretsmanager_secret_version.db_password.secret_string
```

**Scan for secrets with git-secrets or tfsec:**
```bash
# Install tfsec
brew install tfsec   # macOS
# or: https://aquasecurity.github.io/tfsec

# Scan your Terraform code
tfsec .
```

### 11.4 Reusable Module Design

Structure a reusable module under a `modules/` directory:

```
terraform-aws-lab/
├── modules/
│   └── web_server/
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
├── environments/
│   ├── dev/
│   │   ├── terraform.tf
│   │   ├── main.tf
│   │   └── terraform.tfvars
│   └── prod/
│       ├── terraform.tf
│       ├── main.tf
│       └── terraform.tfvars
```

Example module call in `environments/dev/main.tf`:
```hcl
module "web_server" {
  source = "../../modules/web_server"

  project_name  = "myapp"
  environment   = "dev"
  instance_type = "t2.micro"
  vpc_id        = module.vpc.vpc_id
  subnet_id     = module.vpc.public_subnets[0]
}
```

Module design principles:
- Each module should do one thing well
- Expose all tunable settings as variables
- Use `description` on every variable and output
- Pin module versions with `version = "~> x.y"`
- Document usage in a `README.md`

## 12. Troubleshooting Common Issues

### Issue: `Error: No valid credential sources found`

**Cause:** Terraform cannot find AWS credentials.

**Solutions:**
```bash
# Verify credentials are configured
aws sts get-caller-identity

# Re-configure if needed
aws configure

# Or set environment variables
export AWS_ACCESS_KEY_ID="AKIAIOSFODNN7EXAMPLE"
export AWS_SECRET_ACCESS_KEY="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
export AWS_DEFAULT_REGION="us-east-1"
```

### Issue: `Error: Error acquiring the state lock`

**Cause:** A previous Terraform run was interrupted and left a lock in DynamoDB.

**Solution:**
```bash
# List lock info
terraform force-unlock LOCK_ID

# Or manually delete from DynamoDB
aws dynamodb delete-item \
  --table-name terraform-locks \
  --key '{"LockID": {"S": "terraform-state-ACCOUNT_ID/terraform.tfstate"}}'
```

### Issue: `Error: InvalidAMIID.NotFound`

**Cause:** The AMI ID is hardcoded and doesn't exist in your region.

**Solution:** Use a data source to look up the AMI dynamically (as shown in section 3.3).

### Issue: `Error: VPCIdNotSpecified`

**Cause:** Creating a security group without specifying a VPC when non-default VPCs are in use.

**Solution:** Add `vpc_id = module.vpc.vpc_id` to `aws_security_group`.

### Issue: Provider version conflicts after `terraform init`

**Solution:**
```bash
# Delete lock file and re-initialize
rm .terraform.lock.hcl
terraform init -upgrade
```

### Issue: `Error: Resource already exists` after `terraform apply`

**Cause:** The resource was created outside Terraform.

**Solution:** Import it into Terraform state:
```bash
terraform import aws_instance.web i-0abc1234567890def
```

### Enable Debug Logging

```bash
# Linux/macOS
export TF_LOG=DEBUG
terraform apply 2>&1 | tee terraform_debug.log

# Windows PowerShell
$env:TF_LOG = "DEBUG"
terraform apply
```

Log levels: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`
